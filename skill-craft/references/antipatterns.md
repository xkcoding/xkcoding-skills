# 反模式目录

审查时逐条比对。每条给出：症状、为什么会坏、怎么改。

BAD/GOOD 是对照，不是模板——照抄句式没用，要看清它改的是哪种毛病。

---

## 1. 把推断写成了规则

**症状**：句子在陈述一个偏好、优先级或分类，而不是一个客观限制。

```
BAD   URL 是实现细节，UI 才是稳定约定        → agent 硬编码为：必须走 UI，哪怕有现成 API
GOOD  凭记忆构造的 URL 常缺少会话参数，会被拦；从页面交互得到的链接自带完整上下文
```

**为什么坏**：推断是你在某个具体情况下得出的结论。写成规则之后，agent 会在你没预料到的情况下照样执行。给它原始事实，它能得出同样结论，也能在不适用时绕开。

**怎么改**：把"所以应该…"删掉，只留"因为…"。

---

## 2. 锚在行为上，不是思维上

**症状**：比喻或指令描述的是动作。

```
BAD   像人一样浏览网页       → 去模拟鼠标移动、逐像素滚动，11 步
GOOD  像人一样思考            → 带着目标进入，边看边判断，3 步
```

**为什么坏**：agent 会把比喻落到最字面的那一层。

**怎么改**：把动作换成意图。"怎么做"换成"要达成什么"。

---

## 3. 过度详细

**症状**：一串对 agent 来说本来就会做的步骤。

```
BAD   Step 1: 打开首页 → Step 2: 找到搜索框 → Step 3: 输入关键词 → Step 4: 点击搜索
GOOD  目标：在 X 平台找到账号 Y 的主页
```

**为什么坏**：步骤锁死了路径。搜索框换了位置、有了直达 URL，agent 还在照着第一步走。

**怎么改**：删掉步骤只留目标。**判断标准**：删掉之后 agent 能否做得一样好或更好？能，就删。

**但是**——操作脆弱的地方相反：一条命令参数少一个就挂死，那就把完整命令写出来，或者干脆进脚本。详细程度要配脆弱性，不是越少越好。

---

## 4. 用词暗示排他

**症状**：把并列的能力写成了一组互斥的选项。

```
BAD   你可以使用以下通道之一：A / B / C
GOOD  可用工具：A、B、C，可以组合使用
```

**为什么坏**："通道""模式""路径"这类词读起来像单选题，agent 会选一个然后从一而终，即使组合起来更好。

**怎么改**：换成"工具""能力""选项"，并明说可以组合。

---

## 5. 详细程度配不上脆弱性

**症状**：脆弱的操作只给了目标；开放的任务却给了死步骤。

| 任务性质 | 该给什么 |
|---|---|
| 多种方案皆可 | 目标 + 约束 |
| 有推荐做法 | 模板 + 示例，并说明什么时候可以偏离 |
| 操作脆弱、错一次要重来 | 完整命令，或者直接进脚本 |

**怎么改**：先判断这件事错了的代价，再决定写多细。

---

## 6. 该进脚本的留在了散文里

**症状**：SKILL.md 里有一串 shell 片段，要 agent 每次照着敲；或者一段多步骤流程，中途失败需要回滚。

**为什么坏**：每次重敲都可能敲错，而且错法每次不同。真实例子：一个"创建失败后仍继续搬文件"的流程，靠读是发现不了的，跑起来就把目录搬错了地方。

**怎么改**：写成脚本，输出结构化结果，把守卫和回滚放进去。SKILL.md 只说"跑哪个子命令、按结果怎么办"。

**反向也是反模式**：把需要看一眼再决定的事写成固定流程（"空闲就发续跑指令"——可它其实是在等用户回答问题）。

---

## 7. 链接到目录之外

**症状**：`../`、指向仓库根、指向兄弟 skill、指向作者机器上的绝对路径。

**为什么坏**：skill 目录可能被单独复制走。链接一旦断掉，那一段就指向了空气。绝对路径在别人机器上永远不成立。

**怎么改**：共用的约定就地内联一份；路径用 `${CLAUDE_SKILL_DIR}`。宁可重复，不要跨目录引用。

---

## 8. reference 链成了链

**症状**：SKILL.md 指向 A，A 又指向 B。

**为什么坏**：读的人已经跳了一次。第二跳的内容多半根本不会被读到。

**怎么改**：B 要么并进 A，要么直接从 SKILL.md 挂出来，在索引里写清"何时加载"。

---

## 9. 外部行为写成了永恒真理

**症状**："codex 的升级弹层默认项是第一个"——没说哪个版本、哪天看到的。

**为什么坏**：下个版本它就变了，而 agent 会继续照着旧的按。

**怎么改**：

```markdown
- (2026-09-18, codex 0.154) 启动期升级弹层默认高亮"立即升级"；发按键 `2` 选 Skip。
```

并在开头声明：当提示，不当保证；不符就以眼前看到的为准，然后回来更新这份记录。没验证过的说法单独列一节，写明不成立时怎么办。

---

## 10. description 只写了"是什么"

**症状**：`description` 描述功能，但没写用户会怎么开口。

**为什么坏**：决定这个 skill 会不会被想起来的，通常只有 `description` 这一句话。用户不会说"审查 agent skill 质量"，他会说"这个 skill 写得不好"。

**怎么改**：**做什么 + 什么时候用 + 用户的原话**，中英文触发词都写进去。上限 1024 字符，用足。第三人称，不要"我可以帮你…"。

---

## 11. 泄漏了开发过程

**症状**：skill 正文里出现 `D6`、`F12`、`design.md`、`openspec/changes/…`、内部 capability 名。

**为什么坏**：使用者看不到那些东西。这些编号对他是纯噪音，还会让他以为漏了什么必读文档。

**怎么改**：开发过程的编号留在开发产物里。skill 正文只写使用者需要的东西。

---

## 12. 把品味当成了冗余（反向误判）

**症状**：审查者看到大段具体数值——间距、字重、配色、节奏、时长——判为"过度详细"并精简。

**为什么坏**：美学类 skill 里，这些数值就是内容本身。精简掉之后 skill 还在，效果没了。本仓库真实踩过这个坑。

**怎么改**：先问**删掉这个细节还能得到同样的结果吗**。不能，它就是承重的，别动。品味类 skill 的细节通常承重。
