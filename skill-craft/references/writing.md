# 从零写一个 skill

## 放哪

| 场景 | 位置 | 怎么生效 |
|---|---|---|
| 只给自己用 | `~/.claude/skills/<name>/` | 立即可用 |
| 跟着某个项目走 | `<repo>/.claude/skills/<name>/` | 在该项目里可用 |
| 要分发给别人 | 仓库里一个目录 + 注册进 `.claude-plugin/marketplace.json` | 用户装插件后可用 |

开发期想让仓库里的 skill 立刻全局可用，软链接过去即可：

```bash
ln -s /path/to/repo/<name> ~/.claude/skills/<name>
```

## 目录

```
<name>/
├── SKILL.md          入口。原则 + 路由 + 流程
├── scripts/          确定性的操作
└── references/       按需加载的详细内容，一层
```

只有一段内容时就别建 `references/`——写进 SKILL.md 更省一次跳转。

## frontmatter

```yaml
---
name: <与目录名一致，小写字母数字连字符>
description: >-
  <做什么。第三人称，不要"我可以帮你…"。>
  <什么时候用它——把用户可能的说法写进去，中英文都写。>
metadata:
  author: <你>
  version: "1.0.0"
---
```

`description` 是这个 skill 唯一的"被想起来"的机会：上下文里通常只有它，没有正文。上限 1024 字符，把触发词写足——用户说"这个 skill 写得不好"和说"audit prompt"应该命中同一个 skill。

带参数的写 `argument-hint`。

## 什么进脚本

| 进脚本 | 留给模型 |
|---|---|
| 拼命令行参数（少一个就进交互式提问然后挂死） | 读一屏输出决定下一步 |
| 搬文件、改分支、写入前的守卫与回滚 | 判断用户到底想要什么 |
| 解析 JSON / 数据库 / 日志，汇总状态 | 权衡两种方案的取舍 |
| 多步骤且中途失败要回滚的流程 | 写给人看的总结 |

脚本的约定：

- **纯标准库**，除非这个 skill 本来就依赖某个运行时。少一个依赖，少一个装不上的理由。
- **一个子命令输出一个结构化结果**（JSON 最省事），失败时说清**为什么拒绝**——拒绝是信息，不是要绕过的障碍。
- **永不崩溃**。抓住异常，输出成结果的一部分。模型能处理 `{"ok": false, "error": "…"}`，处理不了一个 traceback。
- **路径用 `${CLAUDE_SKILL_DIR}`**，不要写死作者机器上的绝对路径。
- 有多个入口就用**子命令**（`plan` / `create` / `list`），不要拆成一堆小脚本。

## references 怎么切

按**什么时候需要读**切，不是按主题切。SKILL.md 末尾给一张索引：

```markdown
## References 索引

| 文件 | 何时加载 |
|---|---|
| `references/<x>.md` | <什么情况下才需要打开它> |
```

规则：

- **一层。** reference 不要再链接到另一个 reference——读的人已经跳了一次，不要再跳。深层内容要么合并，要么直接从 SKILL.md 挂出来。
- **一组可互换的文件**（每个站点一份、每种风格一份）放进 `references/<group>/`，在 SKILL.md 里说明"按模式加载"即可，不必逐个列出。
- **不链接目录之外的任何东西。**

## SKILL.md 怎么组织

```
定位          一两句：这个 skill 是干什么的，和相邻的东西怎么区分
路由          一张表：什么输入 → 走哪一节。不要写散文式的条件分支
前置检查      需要外部工具的话，怎么查、缺了怎么办（只检查，不擅自安装）
原则          几条心法，每条带"为什么"——这是 agent 遇到没写到的情况时的依据
脚本          一张表：每个子命令干什么
流程          按路由分节
技术事实      外部工具的行为，标日期和版本
References    索引
```

**先原则后流程**，因为现实一定会超出你写的流程；agent 手里有原则才知道怎么办。

篇幅没有硬上限。常见的 skill 落在 150–300 行；品味类的更长是正常的。真正的标准是：**每一句都在给它不知道的东西**。

## 写完怎么测

1. **跑检查脚本**，把 `flags` 清空。
2. **用真实输入走一遍完整流程**，不是读一遍。上一个 skill 的三个 bug 全是跑起来才现形的，读代码一个都没发现。
3. **测边界**：缺依赖、外部工具报错、用户中途改主意、并发跑两个。
4. **让一个新会话只凭 `description` 触发它**——描述不对，这个 skill 等于不存在。

## 写完之后

用一段时间，把遇到的真实行为回填进"技术事实"。**只写验证过的，不写猜测**；没验证的单独列一节，并写明不成立时怎么办。
