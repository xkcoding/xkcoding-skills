# 写打分器

循环里只有一处地方决定了几十轮之后会得到什么，就是打分器。agent 换一个、prompt 改一遍，影响都远小于把分数的定义改一个字。

## 契约

可执行文件，从仓库根运行，stdout 打印**一个 JSON 对象**：

```json
{
  "score": 155.95,
  "version": "5.1.0",
  "details": {"cases": 90, "redundant": 2, "values": "66/66", "pairs": "1879/1904"},
  "remaining": ["gauge.orientation=vertical", "gauge.showThresholdMarkers × calcs=last"],
  "timings_ms": {"observe": 228000, "judge": 516000}
}
```

- `score` 必须是数字，越大越好（`research.json` 里 `direction: "min"` 可反过来）。
- `version` 必填。runner **只在同一个版本内比较分数**；版本一变，下一轮先在 HEAD 上重测一次作为新基线，旧记录原样保留，报告里换一条色带。
- `details` 任意 JSON，报告原样展示成表格——给人看"分数是怎么来的"。
- `remaining` 字符串数组，下一轮的 prompt 会原样带上。
- `timings_ms` 可选，打分器自报子阶段耗时，报告里和 agent / gate / score 并列。

退出码非 0、stdout 不是合法 JSON、缺 `score` 或 `version` → 这一轮记为 **error**：撤回、单独计数、不占 discard 配额。打分器坏了不是 agent 的错。

环境里能拿到：`AR_REPO`、`AR_SUBJECT`、`AR_ROUND`、`AR_CHECKPOINT`、`AR_ARTIFACT_DIR`（要写中间文件就写这里，**不要往仓库里写**——仓库里的任何新文件都会被算进这一轮的改动）。

`gate` 是另一回事：退出码 0 = 通过，非 0 = 这一轮 crash 且**不打分**。gate 放"连测都不值得测"的检查：编译、lint、schema、冒烟。它每轮都跑，agent 自己也可以随便跑，所以要快。

## 开循环之前手跑三次

一个坏打分器要几十轮、几美元才看得出来；三次手跑几分钟就能排掉大部分。手跑时没有 `AR_*` 环境变量，打分器要能没有它们也跑（写中间文件就落到 `tempfile`）。

1. **合不合契约。** 从仓库根 `./autoresearch/subjects/<name>/score`，stdout 只有一个 JSON、有 `score` 和 `version`、`remaining` 是字符串数组。stderr 随便写，runner 不看。
2. **分得出好坏吗。** 拿两个已知一好一坏的版本（git 里随便挑两个 commit，或者故意删掉一半测试）各跑一次。分数差距对得上你的直觉吗？两边差 0.01 而你觉得天壤之别——打分器不敏感，循环会在噪声里"进步"。
3. **一轮能推进多少。** 想象一个强模型一轮合理的工作量，它能把分数推多远？推不动（比如分数只在整个功能完成时才跳）——agent 得不到梯度；一轮推到顶（见下面"一轮能打满"）——第二轮无事可做。两种都要先改打分器再开循环。

## 五个真实的坑

**没有分项的维度，不会得到任何投入。** 这不是 agent 偷懒，是它在按你写下的定义优化。想要代码更快就得有耗时项，想要更少冗余就得有冗余扣分。反过来，**凡是你没打分却在意的东西，几十轮之后一定会变差**——这是这套机制最可靠的现象。

**打分器对你真正关心的改动不敏感 → 假进步。** 分数在涨、曲线很漂亮、东西没变好。自检办法：手里现成的两个版本（一个明显更好、一个明显更差），各跑一次打分器，分数的差距对得上你的直觉吗？对不上就先修打分器，别开循环。

**一轮能打满的打分器，第二轮就无事可做。** 真实踩过：一个"覆盖 12 个特性和 66 个两两组合"的打分器，模型第一轮写了 4 条巨型用例就 12/12、66/66，后面全是 discard。加一条"单个用例最多算 4 个特性"的上限之后，同样的目标需要约 28 条用例，才变成一个几十轮的研究。
设计时就该算一下：**一轮合理的工作量能把分数推进多少？** 推不动是坏的，一轮推到顶更坏。

**组合覆盖要给低权重。** 单项 ×1、两两组合 ×0.05 这种配比不是美学：组合的数量是平方级的，给高了分数就只剩组合，agent 会去堆组合而不去补没覆盖的单项。

**重复要扣分。** 没有冗余惩罚时，"再写一条和已有用例等价的"永远是最省力的涨分方式。扣分要大于它能骗到的分（示例里是 −2 对 +0.05）。

## `remaining` 怎么写

这是 harness 无状态的全部依据：下一轮的 agent 不记得上一轮，它只知道 prompt 里的这份清单。

从度量里**直接导出**，不要另写一套：

| 度量 | `remaining` |
|---|---|
| 覆盖率 12/66 | 没覆盖的那些的名字 |
| 测试通过 48/55 | 失败的 7 条，每条带期望与实际 |
| 延迟 p95 = 820ms | 最慢的几个端点与各自耗时 |
| LLM 评分 7.2/10 | 评委扣分的具体条目 |

写不出来，通常说明这个分数是个黑箱——那样的循环只能靠随机试探前进。清单可以长（prompt 里截到 200 条），空清单意味着"按这把尺子已经没事可做了"，循环会一路 discard 到停。

## 保护分数

锁定路径（`locked`）能挡住"改打分器 / 改测试集 / 改期望值"这类直接作弊：被改到就在 gate 之前判 crash，连分都不打。`autoresearch/**` 永远在锁定列表里；**把一切改了就能让分数虚高的东西也放进去**——隐藏的参考实现、期望输出、评测集。

锁定挡不住"把答案硬编码进实现"。那是打分器自己的事：

- 期望值由**锁定目录里的参考实现**现算，而不是读 agent 自己写的那份（示例 kata 的 impl 打分器就是这么做的——否则 agent 只要把测不过的用例改掉就能涨分）。
- 两个 subject 互相锁：写用例的那个不能碰实现，写实现的那个不能碰用例。
- 怀疑时看报告里的 `changed_files` 和 agent 自述——每一轮改了哪些文件都在账本里。

## 用 LLM 当评委

有时候只有模型能判断（文风、图像相似度、"这段解释清楚吗"）。可以用，但要知道代价：

- **贵且慢。** 评委的耗时可能超过 agent 本身（参照过的一个真实研究里，评委 8.6–17.7 分钟，agent 6.6 分钟），而且每轮都要花一次。用 `timings_ms` 把它单独报出来，预算才看得见。
- **有随机性。** 同一份代码两次分数不同，循环就会靠噪声"进步"。对策：评委固定 temperature 与 prompt、必要时多次采样取中位数、把评分粒度做粗（1–5 而不是 0–100）。runner 不替你去噪，它只保证**分数相等算 discard**，不会把噪声当进展留下。
- **能作弊。** 评委也是个可以被讨好的模型。尽量把能确定性计算的部分（数量、覆盖、通过率）算出来，只把真正主观的那一点交给评委。

## 改打分器

改 `score` 的同时 bump 它自报的 `version`，没有例外。忘了 bump，新尺子量出来的分会和旧尺子的分直接比较，best 可能被一个根本不可比的数字顶掉。

改完不用重启循环：runner 每轮开始前都会检查工作树，把 `autoresearch/` 下的手改单独提交成 `ar scorer <subject>`，下一轮就用新的打分器。版本变了的那一轮会先在当前 HEAD 上重测一次，作为新版本的基线。
